## 为什么要有这个

和智能体一起开新项目时，通常总会重复做同一套事：

- 写第一版 `README`
- 解释项目结构
- 定义编码规则
- 补环境准备说明
- 每次新仓库都重新讲一遍上下文

`start-vibe-coding` 的作用，就是把这些重复动作沉淀成一份可复用协议。靠一个文件，就让智能体拥有足够稳定的上下文来把项目骨架搭起来，而不是靠一轮轮聊天补说明。

---

## 这是什么

`start-vibe-coding` 是一个轻量的仓库初始化协议，核心围绕 `INIT.md`。

它帮助智能体在新仓库里一次性建立：

- 面向人的文档
- 面向智能体的长期工作规则
- 合理的仓库默认配置
- 与项目目标匹配的最小可用结构

---

## 如何使用

### 1. 把 `INIT.md` 放进你的新仓库

把协议文件复制到你想初始化的项目根目录。

### 2. 告诉智能体你要做什么

用自然语言描述你要构建的产品、工具、应用、脚本或库。

### 3. 让智能体按协议初始化仓库

示例提示词：

```text
I want to build a personal expense tracker web app.
Initialize this project following INIT.md.
```

接下来智能体就应该能够：

- 创建要求的文件
- 按项目目标填充内容
- 建好默认的本地环境基础设施
- 建立最小可用结构
- 保持面向人类与面向智能体的文档一致

---

## `INIT.md` 会创建什么

这份协议会定义一套紧凑但完整的起步文件：

- `README.md` 用于项目概览和使用说明
- `PROJECT_LOG.md` 用于追加式开发记录
- `SPEC.md` 用于项目地图
- `AGENTS.md` 用于长期有效的编码与协作规则
- `CLAUDE.md` 作为轻量级智能体入口
- `.gitignore` 用于忽略本地和生成文件
- `requirements.txt` 作为默认依赖清单
- `LICENSE` 用于从第一天起明确许可协议

默认情况下，协议还会约定在仓库根目录使用 `.venv`，这样 Python 工具链、依赖安装和智能体工作规则都能对齐到同一个本地环境。

---

## 为什么这种方式有效

这个协议把面向人的文档和面向智能体的文档明确分开。

| 面向对象 | 文件 | 作用 |
| --- | --- | --- |
| 人类 | `README.md`, `PROJECT_LOG.md` | 介绍项目、说明使用方式、记录进展 |
| 智能体 | `SPEC.md`, `AGENTS.md`, `CLAUDE.md` | 定义结构、规则和执行预期 |

这种分层能明显降低协作摩擦：

- 人类读到的是熟悉的项目入口
- 智能体拿到的是明确的工作规则
- 随着仓库演进，双方上下文更容易保持一致

---

## 为什么智能体文件很重要

大多数项目都有 `README`，但很少项目会把给编码智能体的长期规则也当成基础设施来维护。

`start-vibe-coding` 把这些文件视为一等公民：

- `AGENTS.md` 存放长期有效的工作规则
- `CLAUDE.md` 保持轻量，只负责把智能体导向这些规则
- `SPEC.md` 让仓库地图能够快速重载

这样，智能体依赖的是稳定的项目上下文，而不是每次都靠聊天重新解释一遍。

如果项目有需要，也可以支持多语言文档，比如 `README.zh.md`。
